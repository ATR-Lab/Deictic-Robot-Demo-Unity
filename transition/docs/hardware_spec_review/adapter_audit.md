# Hardware adapter audit for implementation/testing specification

Scope: current `backends/booster_backend.py`, `runtime.py`, `backends/base.py`, `docs/HARDWARE_INTEGRATION.md`, and `tests/test_booster_backend.py`. Read-only code audit plus one isolated fake-transport probe; no SDK client, DDS connection, robot contact, or physical command. No source code or final specification was changed. Existing documentation's SDK facts were not freshly re-verified against the vendor.

## Exact interfaces and data

All shared backend times are seconds in the runtime monotonic domain. The concrete SDK transport uses the host's **absolute** `time.monotonic()`, so a live runtime must use that same domain, not a zero-based logical-run clock.

| Interface | Current contract |
|---|---|
| `PointProfile(hand, position_m, orientation_rpy, duration_ms, target_label, position_tolerance_m, settling_seconds)` | One local named endpoint profile. Hand is left/right, position/orientation each three finite numbers; positive requested duration, position tolerance, and dwell. No reachability, collision, joint-limit, orientation-range, or profile-label mapping check. Orientation is commanded but not verified. |
| `K1Config(expected_serial, expected_firmware, allowed_mode, allowed_body_control, profiles, commissioning_receipt, physical_actuation_enabled=False, max_state_age=0.25, max_arm_speed=0.05)` | Exact expected identity/mode, nonempty profile dictionary whose keys are a subset of `point_a`, `point_b`, `home`, and nonempty receipt string. Thresholds are configuration defaults, not commissioned values. `max_arm_speed` applies to measured joint velocities, hence must be documented/calibrated as radians/second, not Cartesian speed. |
| `K1Sample(sampled_at, serial, firmware, model, mode, body_control, arm_positions, arm_velocities, hand_positions, motor_lost=False, site_ready=False, timestamp_source='source_monotonic')` | Eight arm joint positions/velocities; hand XYZ dictionary; one sample time and composite readiness Boolean. No source sequence, robot boot epoch, acquisition interval, sensor-skew bound, ownership token, or support/contact measurement. |
| `K1Transport.read() -> K1Sample`, `move(profile) -> None`, `stop() -> None` | Synchronous transport boundary; no timeout/cancel argument, command ID, session epoch, or receipt returned by robot. |
| `BoosterK1Backend(config, transport, journal)` | Configuration validation, same-ledger `flock`, SQLite FULL synchronous command/event ledger; no connection or arming by this constructor. |
| `arm(now, *, commissioning_receipt) -> None` | Requires enabled configuration, matching receipt string, no nonterminal ledger command, checked identity/state/site readiness, and both arms below speed threshold. Sets armed and clears adapter fault. It is not a scoped runtime authority grant. |
| `start(command, now) -> BackendEvent` | Accepts only `kind='point'` and exactly `parameters={'profile': name}`; admits one active command. Persists intent before move RPC; return without exception yields `accepted`, not success. |
| `poll(now) -> list[BackendEvent]` | Produces measured success/cancel or unknown; never invents logical fixture effects. |
| `observe(now) -> Observation` | Reports connectivity, fresh-state timestamp, adapter boot UUID, active project command ID, quiescence/fault, and `remote.pointed_target` evidence. |
| `request_stop(now) -> None` | Requests planner stop when adapter has an active command. Not an emergency-stop implementation or proof of stopping. |
| `command_status(id, now) -> BackendEvent | None` | Returns last persisted adapter receipt, not a fresh query of robot execution history. |
| `close() -> None` | Closes SQLite/file lock only; sends no robot command, makes no stop assertion, and does not close the supplied transport. |

`SkillCommand` fields are `command_id`, `run_id`, `skill_id`, `kind`, `parameters`, `dependency_versions`, `authority_id`, `authority_revision`, `issued_at`, `deadline`. The backend retains these in its payload but does **not** independently validate dependency versions or authority grants. The runtime is the current enforcing task layer.

`BackendEvent` carries command ID, status (`accepted/running/succeeded/failed/canceled/unknown`), time, fact updates, detail, and evidence. `FactUpdate` carries value, observation time, optional expiry, known/unknown/conflict status, and source. `Observation` carries connected/quiescent flags, observation time, adapter boot ID, facts, active command ID, and optional fault.

## Concrete SDK transport

`BoosterSDKTransport(*, network_interface, domain_id, robot_name, permit_connection, site_ready)` checks explicit connection permission, nonempty interface, and installed Python distribution version `1.6.3`; it then initializes the SDK channel factory, `B1LocoClient`, and low-state subscriber. The configured wheel hash is **not** checked here.

- Low-state callback requires exactly 22 motors, reads arms at indices 2:10, and records whether **any** motor reports lost. Timestamp is callback receipt time. Old delayed packets can therefore look newly received.
- `read()` captures the latest low-state tuple, separately performs `GetRobotInfo`, `GetStatus`, and body-to-left/right-hand `GetFrameTransform`, then evaluates `site_ready()`. This is not an atomic multisensor sample. The transforms are kinematic/model-derived evidence, not independent target metrology.
- `move()` constructs `Posture(Position, Orientation)` and invokes `MoveHandEndEffectorV2(..., duration_ms, HandIndex)`. `stop()` invokes `StopHandEndEffector()`. No gait/mode/raw-joint/whole-body control is implemented.
- `BoosterSDKTransport.close()` closes only the subscriber channel. No lifecycle supervisor or bounded SDK worker process is implemented.

## Existing guards, completion, and recovery behavior

`_checked_sample` checks exact serial/firmware, model name K1, finite/fresh timestamp (including elapsed read-call time), eight finite arm positions/velocities, configured mode/body-control, no motor-loss indication, positive site readiness, and finite three-component hand transforms. It does not require all relevant hand keys until they are accessed later; it does not check physical joint envelopes or torso/support state.

`start` requires its deadline to be strictly later than entry time plus requested motion duration and dwell. Accepted motion invalidates the pointing fact. `poll` requires both arms below the configured speed threshold and the selected hand within position tolerance; these conditions must persist over **advancing sample timestamps** for the configured dwell. A large sample gap resets dwell; regression yields unknown. A repeated unchanged timestamp does not accumulate dwell. Success emits only `remote.pointed_target=label`, with expiry `sampled_at + max_state_age`, endpoint evidence, frame `torso`, and `orientation_verified=False`.

Subsequent `observe` refreshes that label only while the same completed profile remains within tolerance, arms are stationary, no adapter fault exists, and no command is active. Otherwise the fact is unknown. Labels mean named endpoints, not independently verified pointing-ray/object correspondence. Restart preserves prior receipts but loses live completed-profile identity, so an old success receipt is not a fresh known target observation.

Normal stop sets a flag; advancing stationary samples over the dwell produce `canceled` with no task effects. Poll failure produces `unknown`, disarms, retains the active command, and latches adapter fault; subsequent `poll` returns nothing while faulted. An observe-only exception returns disconnected/fault evidence but does not itself mutate the adapter's armed flag; the runtime latches the fault. Stop RPC exceptions persist unknown and disarm.

The runtime serializes access; rechecks authority/freshness after observation and intent persistence when a live clock is configured; binds dependency versions; and blocks common return conflicts. Supported terminal effects must exactly match one declared outcome footprint/status with adequate timing/freshness. Completion credit now additionally waits for observed quiescence. Partial effects remain recorded; unknown and failed/canceled outcomes do not produce completion. Runtime reconciliation is read-only and never clears faults or replays motion. Existing journals cannot automatically restart a runtime.

Adapter deduplication compares full command plus configuration for **persisted** command IDs. Some pre-admission failures return a failed event without adding an adapter ledger row. A second adapter using the same journal is excluded, but another ledger path can create another owner. SQLite/file locks are not robot-wide command fencing.

## Concrete gaps to turn into implementation requirements

1. **Idempotent stop request/state machine.** `Runtime._latch` calls `request_stop` on each persistent-fault invocation. `BoosterK1Backend.request_stop` resets both dwell fields on every call. Repeated revocation/invariant/overrun ticks can therefore prevent canceled completion forever, even with stationary advancing samples. Fake probe: four repeated stops at 1.05/1.15/1.25/1.35 produced four stop RPC calls, no terminal events, active command retained, and ledger still `accepted`. Latch a stop epoch once, preserve its dwell across duplicate requests, bound stop completion, and define independent emergency escalation. Faulted `poll` currently cannot confirm later stopping, so explicit reconciliation must cover that path. Also, `request_stop` is a no-op when the adapter has no local active command: it cannot stop unowned motion.

2. **Bounded I/O and final dispatch timing inside the adapter.** Runtime's final check precedes the adapter's own blocking state queries and ledger commit. Adapter deadline is checked only at `start` entry; there is no renewed guard immediately before `move`. `poll` compares deadline against caller-supplied time even after blocking reads. Implement a supervised/bounded transport, refresh clock/state/authority at practical final boundaries, and enforce watchdog/session expiry below the Python worker. Killing an RPC caller cannot retract a delivered command.

3. **Consistent observation epochs and clocks.** Current callback time is not acquisition time; joint data and sequential transform RPCs can differ in age. The runtime evaluates observations against its supplied processing time; a callback captured after that timestamp but during adapter work can appear “future.” Require explicit clock/age conversion and update processing times after blocking acquisition, source/boot epochs, acquisition intervals or justified conservative bounds, stale/reordered packet handling, maximum gaps/skew, and reset semantics. Real receipt-time sampling cannot inherit Isaac source-time guarantees.

4. **Effective physical ownership and live readiness.** Implement the presently injected `site_ready` monitor, including workcell/support, device identity, controller mode, effective command owner, loss of owner, watchdog, and stop state. The SDK receives no project command token; local command correlation is not robot acknowledgement of that token. Demonstrate exclusion of every competing channel and stale sessions at an enforcing gateway/controller. Different ledger paths, vendor interfaces, gestures, and raw publishers must not bypass ownership. Distinguish authorized background stabilization from task-command competition.

5. **Commissioned immutable configuration and richer physical evidence.** Receipt equality currently checks a string, not a verified signed/hash-bound commissioning artifact. Frozen dataclasses still contain mutable profile dictionaries. Add a validated immutable manifest binding actual robot/firmware, SDK artifact, model/calibration, profile geometry, joint maps, operating mode, thresholds, stop envelope, and test receipt. Position/orientation and duration type/range checks need strengthening; named labels are not constrained to A/B/home semantics. Validate endpoint feasibility, intermediate-path/body clearance, support, orientation requirements, and any directional pointing/target registration through independently justified measurements. Current code neither enforces a collision model nor proves stable standing.

6. **Recovery and lifecycle tooling.** No approved procedure/API currently resolves an ambiguous ledger command, rebinds a restarted robot/source epoch, or restarts after fault with a durable reconciliation decision. Provide supervised stop/join/transport-close ordering, failure-safe cleanup on partial construction, journal backup/verification, read-only inspection, explicit operator disposition, and a new-session readiness gate. Preserve no-auto-replay; never substitute ledger deletion for recovery.

7. **Production conformance at the shared boundary.** Test terminal observations with fault flags, changed boot IDs, mismatched active ownership, contradictory new facts, expired authority during RPC/verification, and receipt storage failure. The current terminal-quiescence branch directly calls `backend.observe` and checks connected/quiescent/age, bypassing the fuller observation reducer; it does not independently apply its returned facts or check fault/boot/owner there. Concrete Booster normally suppresses quiescence on its own fault, but the shared contract should not depend solely on that convention.

## Existing tests and missing validation

The 13 fake-transport tests cover disabled dispatch; acknowledgement versus completion/dwell; duplicate/changed payload; ambiguous restart without replay; one stop request followed by observed stillness; stale state; raw-payload and identity rejection; same-ledger ownership; durable terminal evidence; repeated timestamp; post-completion expiry/drift; gap/regression; and main-thread to serialized-worker handoff. They do not instantiate `BoosterSDKTransport` or validate real RPC behavior, frames, motion, stopping, balance, or ownership.

Add deterministic fake/fault tests first for the gaps above: repeated stops, stop exception/never-settles, missing hand transform, bad mode/site/motor/finite values, callback timing skew and delayed replay, authority/deadline consumed by blocking operations, configuration mutation, ambiguous start/persistence/restart windows, contradictory terminal observations, and shutdown during motion. Then separately commission on hardware: target metrology and repeatability, observed motion/settling, intermediate-path monitoring, explicit stop/link-loss/owner-loss behavior, restart reconciliation, and measured timing bounds. Do not transplant simulated numeric acceptance thresholds or regard fake-test success as commissioning evidence.

The current CLI and isolated ROS gateway do not expose physical hardware selection. A reviewed robot-local deployment assembly and readiness gate remain necessary. No physical profile defaults should be inferred from test fixture coordinates.
