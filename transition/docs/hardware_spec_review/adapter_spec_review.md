# Hardware specification adapter-contract review

Reviewed the draft `docs/HARDWARE_IMPLEMENTATION_SPEC.md` against the current adapter/runtime and the earlier source audit. No specification/code edits, test runs, SDK initialization, or physical execution. The findings below exclude the additional 6 Pro topics the parent is already integrating: source progression versus generated IDs, RPC acquisition caveats, transition/initial regions, effective fencing, stop/success ordering, queued commands at stop, suspend/reboot, attribution, and executable failure gates.

## Material additions or clarifications

1. **Add the terminal-observation bypass to the release blockers and fault matrix.** Section 4.2 correctly requires supported effects and terminal quiescence, but H01–H12 do not include the remaining shared-runtime defect. `Runtime._backend_event` directly calls `backend.observe(now)` and accepts connected/quiescent/age without the normal observation path's fault, boot, ownership, or returned-fact checks. The next ordinary observation can latch a fault only after completion has already been credited. Require a common terminal-observation validator before completion credit/resource release, processing relevant current facts and rejecting incompatible fault/epoch/owner/evidence. Regression cases should provide a nominal supported success followed by a faulted, changed-boot, foreign-owner, or contradictory terminal observation; no completion credit may precede disposition. This is separate from the completion-before-quiescence ordering bug already fixed.

2. **Define how task authority reaches the final enforcing gate.** H04 and Section 6.4 require a last-boundary authority/expiry check, but the existing `SkillCommand` contains only authority ID/revision, and `K1Transport.move` receives only `PointProfile`. Neither boundary conveys a trusted grant's expiry/scope or owner epoch to the component that can actually stop admission. Specify either a trusted live grant resolver at that boundary or a proposed authenticated admission envelope binding command/run/device/configuration, owner epoch, grant ID/revision/scope/expiry, and deadline. Define how revocation reaches the gate and how it checks the commissioned clock domain. Metadata merely logged above the RPC is not enforcement. Preserve the public task command if desired, but explicitly extend the internal physical admission contract.

3. **Clarify processing-time refresh around observations, not just dispatch.** Section 10's shared absolute clock is necessary but insufficient. A source callback can arrive after the runtime captures its `now` argument and before the adapter captures its sample; the generic runtime currently treats that sample as future. Poll/read can also consume time before the deadline is tested against the stale entry timestamp. Require either an explicit as-of cache read bounded by the supplied decision time, or a clock refresh after acquisition before observation/event/authority validation, without rewriting sensor timestamps. Apply this to `observe`, terminal handling, and polling, while retaining separately admitted ingress/deadline timestamps for response ordering. The acquisition-interval model should also explicitly reject nonfinite/reversed/impossibly future intervals; its age/skew inequalities alone do not establish those checks.

4. **Remove ambiguity in the commissioning-manifest digest.** Section 8.1 places `commissioning.manifest_sha256` inside the manifest but does not specify what bytes it hashes. Hashing the complete document is self-referential. Define the immutable canonical payload and excluded receipt/hash fields, or keep the approval/digest in a detached receipt. State how approved identity/profile/calibration values are bound to the parsed runtime configuration and how the loaded configuration is frozen. H09 already requires immutable reviewed configuration; this supplies the missing implementable digest rule. The persistent per-device ledger/registry distinction in Sections 7.4 and H10 is otherwise correct.

5. **Distinguish pre-motion software gates from evidence produced by supervised commissioning.** Section 9 says to resolve H01–H11 before a live motion campaign, while S4 requires those rows passed before profile commissioning. Some rows require the ownership/stop/path evidence that controlled physical stages must produce. Avoid a circular gate by naming the pre-S4 software/enforcement/read-only baseline and the explicitly authorized bounded commissioning envelope, then separately requiring completed physical receipts before ordinary S5 operation or release. The parent’s forthcoming executable-gate additions should make this distinction explicit; a blanket “all rows complete before any live campaign” is not operationally sufficient.

## Otherwise consistent

The draft accurately labels the adapter a prototype and new services/interfaces as required/proposed. Its distinct arm/authority/acknowledgement permissions, idempotent stop episode, continued observation under faults, measured stillness versus unknown task outcome, no-auto-replay, persistent device ledger, strict manifest validation, no automatic home on shutdown, and simulation/hardware evidence boundaries match the source gaps and are usable design directions. The existing stop implementation is not falsely marked fixed. No additional material contradiction was found in those portions.

These findings request specification work, not permission to enable the physical adapter. The code and real device remain unmodified and uncommissioned by this review.
