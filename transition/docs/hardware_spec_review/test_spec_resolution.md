# Test-workflow review resolution

**Reviewed:** 23 September 2026, [hardware implementation specification](../HARDWARE_IMPLEMENTATION_SPEC.md), revision 0.1. Scope: the four material test-workflow findings from the preceding review. This was a document recheck; no code changes, tests, server actions, SDK connection or robot execution were performed.

| Finding | Resolution in the revised specification | Disposition |
|---|---|---|
| **R1 — Commissioning bootstrap cycle** | Sections 8.1 and 8.3 now make prerequisites stage-specific. Observation/discovery can retain unknown calibration/profile values without exposing motion. Bounded profile/stop commissioning uses independent protective prerequisites and its own restricted permit. S5 requires a separately scoped integration commissioning permit after individual transitions pass. Final operational release follows the resulting measurements. Section 9 separates required software regressions from physical evidence still to be acquired. | **Resolved at specification level.** No final-release record is required to obtain the properly authorized commissioning evidence that creates it. |
| **R2 — Collecting “ten valid trials”** | Section 13 now specifies attempted trials by approved transition/start-region stratum, retains failed/interrupted/invalid observations in the denominator, requires predeclared replacement and stop rules, distinguishes pre-dispatch refusal from possible actuation, and rejects attempt N+1 without a new permit. Expected-fault assertion results are separate from measured motion, task outcome and deployment disposition. | **Resolved.** The illustrative repetition count is explicitly exploratory and does not establish reliability or safety. |
| **R3 — Uncertainty absent from acceptance** | Section 6.3 identifies the raw predicate as the current adapter behavior and requires uncertainty-aware commissioned acceptance, including justified registration/velocity terms and declared interval or statistical-coverage semantics. Indeterminate evidence cannot pass; operational tolerance must fit the independently justified error budget. S4 explicitly requires uncertainty-aware checks. | **Resolved at specification level.** Hardware bounds and their validation remain commissioning work. |
| **R4 — Native execution and evidence capture** | Section 12 separates foreground-worker Terminal A from sequential-validator Terminal B, uses a fresh output cohort, captures source/configuration, actual image and worker provenance, checks final quiescence/boot identity, and archives worker artifacts after stopping. It distinguishes fresh records from the historical native manifest and requires retaining failures. The final fresh-checkout correction adds `mkdir -p runs` before the exclusive cohort `mkdir`, preserving both parent-directory creation and refusal to overwrite an existing cohort. | **Resolved.** The final `mkdir` correction was confirmed by the parent reviewer; commands were not executed during this recheck. |

The current/proposed distinction remains clear: the named hardware preflight, observer, monitor, launcher and acceptance harness are implementation work items, while the listed local, Isaac and logical ROS entry points exist. Simulator geometry, timing estimators and passing integration receipts are not treated as physical calibration or policy-efficacy evidence.

**Remaining material findings in this review scope: none.** This closes the specification findings, not the hardware release backlog. The required software changes, instrumented commissioning, exact-release-candidate integration reruns and research evaluation retain their stated pending status.
