# Booster K1 deployment: primary vendor source verification

Checked September 23, 2026. Scope: standard K1, named endpoint reaching/pointing, vendor-owned body control. This was a read-only review of public vendor material and local project code. No robot or simulation server was accessed; no SDK client, subscriber, controller, mode change, or actuation was initialized.

The current [vendor motion page](https://docs.booster.tech/docs/developer-guide/cpp/rpc/motion/) lists `v1.3.1.1` for the underlying MoveHandEndEffector RPC, stop, status, and robot-info interfaces; it explicitly says legacy and V2 share an API ID. This is a documentation compatibility floor, **not a verified minimum firmware for the complete proposed K1 deployment**. The same page's newer custom-mode behavior is qualified by firmware `v1.8.0.9`. No site firmware version or mode is chosen in this review.

## Mode, ownership, and transport boundaries

- The [mode enum](https://github.com/BoosterRobotics/booster_robotics_sdk/blob/87a9a26d06a94ddd50968e7576f1170f6fa5a80f/include/booster/robot/common/robot_shared.hpp#L6-L35) distinguishes `RobotMode` from `BodyControl`; their numeric values are not interchangeable. It warns that damping may allow the robot to fall. Prepare describes standing, but that description alone does not establish that the installed hand planner is reachable or that an unsupported stance is safe.
- [ArmController](https://github.com/BoosterRobotics/booster_robotics_sdk/blob/87a9a26d06a94ddd50968e7576f1170f6fa5a80f/include/booster/robot/b1/arm_controller.hpp#L54-L115) is a low-level trajectory helper. Construction enables upper-body custom control and creates a joint-command publisher; a low-state timeout need not abort construction. It must not appear in a read-only discovery or harmless initialization recipe. The project intentionally avoids this path.
- [ChannelFactory](https://github.com/BoosterRobotics/booster_robotics_sdk/blob/87a9a26d06a94ddd50968e7576f1170f6fa5a80f/include/booster/robot/channel/channel_factory.hpp#L24-L46) is process-wide DDS setup. **Documentation ambiguity:** the [architecture page](https://docs.booster.tech/docs/developer-guide/cpp/architecture/) calls argument two a network IP address, whereas the ArmController parameter comment says interface name or address. The project variable `network_interface` is not proof that arbitrary interface names are accepted. Specify and verify a site-provided network selector for the pinned build; publish no guessed IP/interface.
- [RpcClient](https://github.com/BoosterRobotics/booster_robotics_sdk/blob/87a9a26d06a94ddd50968e7576f1170f6fa5a80f/include/booster/robot/rpc/rpc_client.hpp) has request/response correlation and bounded C++ waits. Its `Stop()` closes channels/wakes waits; this is distinct from robot stopping. A correlation UUID does not supply a documented durable, reconnect-queryable history of endpoint execution. Python timeout/exception behavior remains a commissioning requirement.
- No inspected interface establishes exclusive robot-wide ownership or guarantees collision avoidance, stability, or physical stopping. The local journal lock is only process/file ownership. A robot-local monitor must reject competing control, incompatible actions, stale/faulted state, and loss of the commissioned stop/support arrangement.

## K1 joints and observation limits

The [official asset README](https://github.com/BoosterRobotics/booster_assets/blob/3c2dfa99e09beddf092e0d6521dbbcec7e7903ed/README.md) identifies 22 DOF: two head, four per arm, and six per leg. A four-joint arm does not provide arbitrary independent six-dimensional pose control. Reaching a named endpoint also does not prove a pointing ray or orientation condition.

The pinned [K1 joint enum](https://github.com/BoosterRobotics/booster_robotics_sdk/blob/87a9a26d06a94ddd50968e7576f1170f6fa5a80f/include/booster/robot/b1/b1_api_const.hpp#L146-L174) places arms at indices 2–9: left shoulder pitch/roll, elbow pitch/yaw; then the same right-arm sequence. K1 has no waist. These are SDK layout labels, not an imported articulation-order guarantee. The [URDF](https://github.com/BoosterRobotics/booster_assets/blob/3c2dfa99e09beddf092e0d6521dbbcec7e7903ed/robots/K1/K1_22dof.urdf) has `aaleft_shoulder_pitch_joint` and `aaright_shoulder_pitch_joint`; the [CSV motion-name list](https://github.com/BoosterRobotics/booster_assets/blob/3c2dfa99e09beddf092e0d6521dbbcec7e7903ed/src/booster_assets/motions.py) omits those shoulder `aa` prefixes. Use explicit verified mappings.

The [SDK LowState type](https://github.com/BoosterRobotics/booster_robotics_sdk/blob/87a9a26d06a94ddd50968e7576f1170f6fa5a80f/include/booster/idl/b1/LowState.h) contains IMU and parallel/serial motor arrays, with no acquisition timestamp or sequence field in the inspected message. The [ROS MotorState definition](https://github.com/BoosterRobotics/booster_robotics_sdk_ros2/blob/5f9182e1a1b704f65e0065c83a3b6be2d066f3b3/booster_ros2_interface/msg/MotorState.msg) contains `mode`, `q`, `dq`, `ddq`, estimated torque, temperature, lost-packet information, and two reserve fields documented as motor-error flags and communication frequency. Verify units, update/latency behavior, packet-loss reset semantics, fault interpretation, and array mapping on the actual robot. Callback receipt timestamps alone cannot certify source freshness.

## Official ROS 2 package: useful definitions, unsuitable startup example

The [repository README](https://github.com/BoosterRobotics/booster_robotics_sdk_ros2/blob/5f9182e1a1b704f65e0065c83a3b6be2d066f3b3/README.md) describes message/service definitions. The actual [package name](https://github.com/BoosterRobotics/booster_robotics_sdk_ros2/blob/5f9182e1a1b704f65e0065c83a3b6be2d066f3b3/booster_ros2_interface/package.xml) is **`booster_interface`**, despite the enclosing directory name. It declares ROS build dependencies, not a verified ROS-distro compatibility matrix.

The [low-state example](https://github.com/BoosterRobotics/booster_robotics_sdk_ros2/blob/5f9182e1a1b704f65e0065c83a3b6be2d066f3b3/booster_ros2_example/low_level/src/low_level_subscriber.cpp) subscribes to `/low_state`; SDK constants name `rt/low_state`. Do not assume these are interchangeable strings or deploy guessed namespace/DDS mappings. The [RPC example](https://github.com/BoosterRobotics/booster_robotics_sdk_ros2/blob/5f9182e1a1b704f65e0065c83a3b6be2d066f3b3/booster_ros2_example/rpc_client/src/client.py) uses service `booster_rpc_service` and repeatedly sends mode and walking commands. It also invokes API 2012, `SwitchHandEndEffectorControlMode`, which the [newer pinned SDK deprecates](https://github.com/BoosterRobotics/booster_robotics_sdk/blob/87a9a26d06a94ddd50968e7576f1170f6fa5a80f/include/booster/robot/b1/b1_loco_client.hpp#L606-L620): the robot-state-manager backend returns `BadRequest`. **Do not run or adapt that example as a K1 preparation sequence.**

No inspected material establishes an installed `FollowJointTrajectory` action server, ros2_control K1 hardware plugin, or MoveIt K1 driver. The project's `/transition/*` JSON gateway is its own logical/Isaac transport, not a vendor hardware driver.

## Consequences for the deployment specification

The existing [hardware adapter](../../src/transition_autonomy/backends/booster_backend.py) uses the intended V2 boundary and stays disabled by default. Its success claim is positional endpoint reaching plus arm stillness; receipts explicitly leave orientation unverified. The site must supply the independent readiness monitor. Current adapter code does not itself inspect `GetStatus.current_actions`, motor reserve error flags, temperature, fall state, or an external support/ownership/stop signal beyond the injected Boolean. Treat these as explicit monitor requirements, not completed checks.

The defaults `max_state_age=0.25` and `max_arm_speed=0.05` in project code are **implementation defaults, not vendor-approved safety limits**. Approve or replace them through measurement, together with dwell, profile geometry, duration, reachable workspace, body clearance, support, and stop timeout. Serial/firmware equality checks do not commission those parameters. The existing wheel check establishes API availability only.

Before any physical execution, the deployment record needs the exact robot identity/edition/firmware, pinned host and SDK artifacts, verified network selector/domain/name, compatible controller and active-action constraints, local ownership/stop supervision, calibrated endpoint references/profiles, observed timing bounds, and an ambiguous-command recovery procedure. No values for these unresolved site properties are inferred here.
