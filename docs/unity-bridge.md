# Unity and Quest interaction

For installation and the current complete stack, use [the setup guide](setup.md) and [startup runbook](start-demo.md). This page documents Unity interfaces and preserves dated integration results; generated evidence files are local development artifacts described in [the validation record](validation.md).

Open `Deictic-Robot-Demo` in Unity 6000.6.0f1. The supplied ROS-TCP-Connector 0.7.0-preview and URDF-Importer 0.5.2-preview are embedded packages, including their upstream licenses. `ROS2` is enabled for both Standalone and Android; leaving it off on Android would serialize ROS 1 headers to a ROS 2 endpoint.

`Deictic > Create Demo Scene` builds the visual K1 from the pinned URDF/mesh sources in `models/K1`, preserves the existing `SampleScene`, and creates `Assets/Scenes/DeicticDemo.unity` with the existing Meta rig. The generated K1 is a visual kinematic model; Isaac owns physics and measured robot state. Do not add a second physics controller in Unity.

The generated scene uses a stationary MR rig: its inherited `OVRComprehensiveInteractionRig/Locomotor` subtree is inactive, `OVRManager` uses FloorLevel tracking, and legacy `OVRHeadsetEmulator` is Off while Meta XR Simulator supplies emulated tracking. Normal tracked hands/controllers remain available. **Deictic > Configure Stationary Demo Rig** applies these scene overrides to an existing open `DeicticDemo`; scene creation and APK building also apply them. The original `SampleScene` and SDK prefabs remain unchanged. Do not add an artificial eye-height offset on top of FloorLevel tracking.

`Assets/Resources/DeicticSettings.asset` sets the ROS endpoint, synthetic workcell, confidence and timeout. The generated defaults are `syntheticScene=true`, `publishHeadsetCamera=false`, and localhost:10000, intended for a local endpoint or SSH tunnel. Unity's synthetic-scene flag controls scene/input behavior, independently of ROS registration mode. `run_bridge.sh` defaults to `mock`; its `synthetic` mode uses known alignment and its `markerless` mode requires real visual observations. A Quest APK must use a reachable endpoint address or an explicit ADB reverse route, rather than assuming its localhost reaches the workstation.

Controls:

- Point with the tracked right controller; Quest 3S head direction is the gaze substitute.
- Press/release the right trigger / desktop Space: commit a candidate for planning. The ray must hit an explicit target surface. Joining the press with the left trigger suppresses this single-trigger action.
- Hold both index triggers: [bimanual pose IK](arm-teleoperation.md). Each controller supplies position and rotation in the current head-facing frame, relative to the clutch start. Release either to hold; release both before restarting. Protocol v2 requires the updated controller and relay. Verify this mode with Meta XR Simulator before physical headset testing.
- A / Enter: execute the returned simulation preview.
- B / Escape: cancel and clear the preview.
- **User view / Robot camera** button: switch the headset presentation. Aim at the button and press Trigger (or Space), or click with the desktop mouse. V also toggles it. The button remains available when the robot feed is missing.
- Desktop mouse is available in synthetic mode. `OnVoiceTranscript` accepts `reach there`, `execute`, and `cancel`; connect a configured speech recognizer's final transcript to this hook. Recognition itself is not configured.

Nearby head and pointer hits are averaged within 4 cm; otherwise the explicit pointer wins, matching the paper's selection rule. A fresh atomic alignment/status snapshot gates target commits. A preview remains bound to its original goal and alignment epoch: accepted optimizer updates may preserve it only while the backend's cumulative mapped-target displacement stays within 5 mm of the original preview binding. Origin changes, larger displacement and backend invalidation clear it. Current joints and the time-indexed ghost trajectory are rendered independently.

The preview path is stored in the robot base frame and follows updated alignment together with the ghost. Its separate **Committed target** marker shows the exact requested base point, preserving any small IK residual between that request and the path endpoint. If a preview has no locally retained request, the fallback marker is explicitly labeled **Planned endpoint**. These feedback graphics have no colliders and clear on cancel, execute or preview invalidation. An empty old preview arriving while a new request is pending does not erase that new committed point.

The asset's local confidence floor is 0.65, but commits also require the backend's `can_commit` flag; its unchanged confidence threshold is 0.7. The Unity one-second status timeout checks receipt of fresh status, while the backend separately checks the age of the camera observation. These are different clocks and gates.

## Camera view toggle

User view retains the tracked headset viewpoint and MR robot overlays. On an Android Quest build it enables Meta passthrough even when `syntheticScene=true`: the simulated robot and virtual targets appear over the wearer's real surroundings. Synthetic mode in the Unity editor retains the rendered workcell. Non-synthetic mode also enables the passthrough underlay. Displaying passthrough does not enable RGB-camera publishing or validate the physical registration pipeline.

Robot view hides the passthrough layer and presents the robot's paired head-camera images on a world-fixed monitor, labeled **ROBOT HEAD STEREO / ISAAC SIM**. The toggle stays at `cameraControlsWorldPosition` (default Unity `(0,1.25,0.8)` m), with the monitor above it; neither follows the wearer's head. The Resources-backed `CameraViewOverlay` shader uses normal `LessEqual` depth testing, so scene geometry can occlude this world-space UI. Its image material selects the left or right half of a side-by-side (SBS) texture using the XR eye index; a desktop mono camera shows the left half. Text, controls and backgrounds use a separate non-stereo material. Each eye retains its 4:3 aspect ratio, with ROS row order converted for an upright image. Runtime materials are released when the view is destroyed.

The UI button is a Unity `Button`; the existing controller/mouse ray highlights and activates it before target selection. Aim at the fixed button and press Trigger or Space, use the desktop mouse, or press V. The robot image cannot generate a world-space reaching target. Existing preview execution and cancel controls remain available, and switching views alone neither moves nor cancels the robot.

`robotCameraTopic` defaults to `/deictic/camera_view/stereo/image_raw`, with `robotCameraStereo=true`. The relay pairs `/k1/head_camera/left/image_raw` and `/k1/head_camera/right/image_raw` only when both RGB8 images have exactly the same acquisition header stamp, equal dimensions and distinct optical frame IDs. It publishes one atomic RGB8 SBS image with the left eye in the left half, the right eye in the right half, and frame ID `k1_head_stereo_optical`. Each eye is at most 480×360, giving at most 960×360 total at 5 Hz. The common source stamp is preserved; unmatched or stale eyes produce no output, with no wrist-camera fallback. The simulation's 64 mm head-camera baseline is provisional, not hardware calibration. The wrist camera and synthetic headset RGB/depth cameras remain the full-resolution registration inputs.

Unity subscribes only while Robot view is open, uploads the latest complete image and displays connection/frame-age status. A frame older than `robotCameraTimeout` (1.5 seconds by default) is hidden; the relay separately rejects source frames older than one second. `ros2/scripts/run_bridge.sh` starts the display relay automatically. When adding the viewer to an already running bridge, start only `ros2/scripts/camera_view_relay.py` in the same ROS environment/domain, following [the relay startup instructions](../ros2/README.md#robot-head-stereo-display-stream). Do not start another TCP endpoint. Returning to User view or disabling the viewer removes the display subscription; with no remaining display consumers, the relay unsubscribes from both eyes. Isaac disables these head render products when no head-image or CameraInfo subscribers remain. Maximum SBS pixel payload is 5.184 MB/s (about 41.5 Mbit/s) before transport overhead. This display is independent of the registration stream and does not establish physical-camera latency.

Tracking loss blocks target selection, while B / Escape still requests cancel and V can return to User view. Disabling and re-enabling the camera-view component returns to User view with no image subscription.

The application is validated as one scene owning its bridge and ROS connection. Replacing the bridge alone while preserving that connection is outside this lifecycle check; Connector 0.7 retains its topic callbacks, so shared-topic ownership must be handled before supporting that workflow.

Execute sends the exact goal timestamp back on `/deictic/execute_request`. The backend rejects delayed requests for older previews and rechecks freshness, alignment epoch, mapped-target displacement from the original preview, plan age and measured starting joints. Head tracking loss, recentering, tracking-space changes and pause/resume invalidate alignment and cancel pending motion. A newly published status describing an observation from before the event cannot reopen the gate. The ROS backend starts a new graph epoch for these tracking events so old world coordinates do not constrain the new origin. These lifecycle gates have automated tests; physical headset reset behavior still needs device verification.

The embedded connector contains a documented ROS 2 compatibility patch in `LOCAL_CHANGES.md`: `std_msgs/Empty` includes its required dummy byte. Native ROS 2 otherwise discards cancel and legacy execute messages even though the TCP connection appears healthy.

## Frames and timestamps

ROS body coordinates are forward/left/up; Unity is right/up/forward. Conversion is `(x,y,z)_ROS = (z,-x,y)_Unity`. Quaternion conversion is a handedness change, not a single arbitrary 90-degree rotation. Tests cover composition, inverse mapping and optical axes. Transforms are `T_base_headsetWorld`; the inverse places the robot overlay in MR. Do not apply the head pose twice to an already world-space raycast hit.

Synthetic workcell calibration: Unity `worldFromBase` has translation `(0,.9,1.2)` and identity rotation; equivalently ROS `base_from_headset_world = [-1.2,0,-.9,0,0,0,1]`. This is explicitly known simulation calibration, not a measured markerless transform.

Wall-clock seconds are used for shared ROS messages. A request/reply exchange estimates the Unity-to-backend offset using four timestamps. The current source rejects RTT above **80 ms**, selects the minimum-RTT sample within a recent 10-second window, and uses that selected sample's own age for freshness. Rejected replies trigger prompt retries; pause/resume or a detected clock step discards old samples. The 80 ms bound limits modeled offset uncertainty from network asymmetry to 40 ms, below the backend's unchanged 50 ms future-goal allowance. The prior 250 ms rule accepted a 188.2 ms reply during the partial five-target run; targets 1 and 2 completed, but target 3 was rejected for its timestamp. The revised source passed all **32 EditMode tests**, including six clock cases, then the full five-target traversal described below; the current APK includes this correction.

Commits require recent synchronization. Unity applies the selected offset to pose/goal/camera timestamps, rejects stale or out-of-order status, and the backend independently enforces registration and joint-state freshness. This avoids changing either machine's system clock; it does not replace calibration of camera acquisition latency. Do not enable `use_sim_time` on only one side.

The source with the tighter clock rule passed `SelectFiveFixedWorldTargetsThroughMarkerlessRos` at **20:03:28–20:04:07 UTC**, test run **39.176 s**. Independent grounding for targets 1→5 was **0.17/0.78/0.21/0.37/0.66 mm**; measured tool error was **2.62/2.83/3.93/3.56/4.87 mm**. Each preview was reviewed for 4.5 seconds and each completion required actual movement and fresh feedback. The run began at the previous target-2 pose and then traversed 1→5; it is not the paper's mobile-user task or a neutral-start trial. All earlier failed attempts remain in the [validation record](validation.md).

The associated 150-second observer passed all 1516 gate and 453 registration samples, maximum controller age 0.928550 s. A dedicated 30-second target-5 window passed 299/299 gates and 92/92 estimates, maximum age 0.907099 s. These overlapping bounded windows are reported separately and retain the one-second timeout; they do not establish arbitrary-scene or physical reliability.

The Isaac publisher assigns a common ROS wall timestamp when it retrieves a synchronized cached renderer pair. Display/registration age therefore means elapsed time since that source header, not an independently measured exposure-to-display delay. The capture poses and pixels share a renderer reference even though that reference is not transmitted on the ROS messages.

## Optional physical camera adapter

`QuestCameraPublisher` is disabled by default and refuses to run in the editor. On device it uses Meta's timestamped RGB-camera pose, camera intrinsics and RGB frame, with aligned optical-z depth from raycasts into the captured room geometry. Invalid depths are NaN. It publishes one small RGB/depth observation per second, using ROS optical right/down/forward axes. This initial CPU/readback implementation needs hardware latency, crop/orientation and calibration validation before experimental use. Captured room geometry does not automatically track moving tabletop objects.

To enable it, configure MRUK room loading/scene permission, camera permission and passthrough in a physical Quest build, disable `syntheticScene`, and enable `publishHeadsetCamera`. No calibrated wrist camera is available yet. The XR Simulator cannot validate physical passthrough-camera capture or real SLAM drift.

**Deictic > Build Quest Development APK** builds an ARM64 IL2CPP development APK. **Deictic > Configure Quest Android XR** can apply the Android configuration separately without changing the Standalone rig. The Android package identifier is `edu.kent.atr.deictick1`.

```powershell
./scripts/Build-Quest.ps1
# Optional: -ProjectPath 'C:/path/to/separate/Deictic-Robot-Demo'
```

The helper scopes TEMP/TMP to `C:/Users/Public/DeicticJavaTemp` for its child process and restores the shell environment afterward. For another build environment, the equivalent Unity method is `-buildTarget Android -executeMethod Deictic.Editor.DemoSetup.BuildQuest -quit`; environment variable `DEICTIC_ANDROID_OUTPUT` selects the output file. The generated APK uses the synthetic scene and localhost endpoint. With an authorized USB-connected Quest, `adb reverse tcp:10000 tcp:10000` routes that endpoint to the host's existing ROS SSH tunnel. For wireless operation, configure a reachable ROS host in `DeicticSettings` before building. Building an APK does not test headset permissions, camera capture or physical tracking.
